# Promotion `webassistant-contract/v0.2` / `webassistant-conformance/v0.2`

## Статус и база

Этот design фиксирует одобренную архитектуру promotion после migration audit #100 и product decision #106.

База на момент фиксации:

```text
main = 31291009df693e82599578036ce81988066ae1a9
current accepted pair = webassistant-contract/v0.1 + webassistant-conformance/v0.1
```

Accepted v0.1 остаётся неизменяемой исторической парой. Promotion создаёт новую accepted pair v0.2 и только после этого переключает `repo-policy.json` на неё как на current semantic baseline.

## Цели

- восстановить применимые normative details, найденные #100 как потерянные при semantic rebaseline;
- зафиксировать capability-scoped scanner boundary из #106;
- сохранить все существующие v0.1 requirements, кроме version-specific формулировки baseline в `WA-FS-002`;
- связать восстановленное evidence из #101–#105 с новой conformance pair;
- подготовить стабильный semantic baseline для #98;
- не менять observable product behavior в этой promotion sequence.

Не входят в scope: clean fully-offline build #94, реализация #98, docs audit #99, selective CI #6, новые OCR/editor/signing/upload/auth/filesystem HTTP capabilities и любые product-source changes.

## Семантический delta v0.2

Существующие 16 requirements v0.1 сохраняются. `WA-FS-002` становится version-neutral: browser-facing filesystem routes не публикуются в current baseline, а их добавление требует отдельного contract change с сохранением rooted filesystem boundary.

Добавляются семь атомарных requirements.

### `WA-CI-001` — product-local CI

Автономный export root содержит собственный `.gitlab-ci.yml`, который после экспорта работает без файлов родительского development repository.

### `WA-API-002` — только versioned REST operations

Machine REST operations публикуются под major-version prefix `/v1`; unversioned aliases, включая `/health` и `/scan`, отсутствуют.

### `WA-TRANSPORT-001` — raw PDF transport

Успешная scanner operation возвращает документ как binary `application/pdf` body. Base64, JSON document envelope, ZIP/raster envelope не являются допустимым scanner document transport.

### `WA-SCAN-004` — acquisition/handoff boundary

Один physical acquisition возвращает один PDF, содержащий все страницы этого acquisition. После handoff PDF вызывающей стороне scanner operation заканчивается и не хранит завершённый scan document как long-term scanner storage.

### `WA-SCAN-005` — capability-scoped exclusions

Scanner operation сама не выполняет edit/merge/split PDF, OCR/annotation/watermark/deskew/semantic document transformation, signing/encryption, business/backend upload и не требует business authentication или per-user business profile.

Это ограничения scanner capability, а не глобальные запреты WebAssistant. Любая будущая независимая capability этого типа допускается только через отдельный contract/conformance change.

### `WA-LOG-002` — daily logs без automatic retention

Технические события WebAssistant записываются в собственные суточные log files; current service сам не выполняет automatic retention/delete старых daily logs.

### `WA-DOC-002` — language policy anchor

Новая и изменяемая product/development документация и source comments пишутся на русском языке; технические идентификаторы и термины могут оставаться нерусскими.

## Conformance model v0.2

Сохраняется текущая единая структура `vectors[]` с `id`, `requirements` и `evidence`. Каждый vector получает два явных поля:

```json
{
  "kind": "positive | negative",
  "assertion": "нормативно проверяемое утверждение"
}
```

Это делает negative semantics явной, но не пытается в той же транзакции реализовать executable trace graph из #98.

Целевой набор — 17 смысловых vectors:

1. `WA-C-AUTONOMOUS-ROOT-001`;
2. `WA-C-PRODUCT-LOCAL-CI-001`;
3. `WA-C-SERVICE-LIFECYCLE-001`;
4. `WA-C-LOOPBACK-001`;
5. `WA-C-VERSIONED-API-001`;
6. `WA-C-SCANNER-HTTP-001`;
7. `WA-C-MULTIPAGE-001`;
8. `WA-C-RAW-PDF-TRANSPORT-001`;
9. `WA-C-SCANNER-BOUNDARY-001`;
10. `WA-C-SCANNER-EXCLUSIONS-001`;
11. `WA-C-DIAGNOSTICS-001`;
12. `WA-C-DAILY-LOG-001`;
13. `WA-C-CORS-001`;
14. `WA-C-ROOTED-FILESYSTEM-001`;
15. `WA-C-DEPENDENCY-OWNERSHIP-001`;
16. `WA-C-PRODUCT-DOCS-001`;
17. `WA-C-LANGUAGE-POLICY-001`.

`WA-C-SCANNER-EXCLUSIONS-001` перечисляет отдельными clauses все scanner-scoped exclusions из `WA-SCAN-005`; это не считается доказательством будущих whole-product запретов.

Evidence v0.2 включает существующие core/platform surfaces и восстановленные #101–#105 paths, в частности `WindowsPowerShellCompatibilityTests`, `IsolatedExportRootAcceptanceTests`, `LinuxScanAdapterTests`, `DependencyOwnershipTests`, `RuntimeOptionsTests` и соответствующие platform workflows.

Promotion не вводит искусственные новые product tests только ради формального увеличения evidence. Текущий 3-page ADF fixture и platform acquisition остаются evidence для multipage semantics; current logger implementation остаётся evidence отсутствия automatic retention/delete. Если #98 после promotion докажет, что этого evidence недостаточно для fail-closed graph, это создаёт отдельный remediation item; contract не ослабляется задним числом.

## Транзакция A — current-pair-aware baseline test

Scope:

```text
tests/core/BaselineContractTests.cs
```

Тест перестаёт жёстко знать filenames/schema v0.1 и вместо этого читает `contract_conformance.current` из `repo-policy.json`.

Он fail-closed проверяет:

- current contract/conformance files существуют;
- оба имеют accepted state, требуемый policy;
- `conformance.contract` равен `contract.schema`;
- `contract.conformanceCorpus` указывает на current conformance path;
- `repositoryModel.exportRoot` остаётся `webassist`;
- каждый `requiredRepositoryPaths` entry существует.

Current v0.1 обязана оставаться GREEN. Ни contracts, ни policy, ни README, ни product files в этой транзакции не меняются.

## Транзакция B — root README preparation

Scope:

```text
README.md
```

README сохраняет ссылки на accepted v0.1 как историческую pair и добавляет v0.2 как следующую/current после promotion. Старые ссылки не удаляются.

Это отдельная docs-only транзакция; contracts и policy в ней не меняются.

## Транзакция C — atomic governance promotion

Scope строго ограничен:

```text
repo-policy.json
contracts/webassistant-contract-v0.2.json
contracts/webassistant-conformance-v0.2.json
```

Для транзакции требуется GovernanceGrant без policy relaxation.

Promotion выполняется атомарно:

- создаётся v0.2 contract;
- создаётся v0.2 conformance;
- `contract_conformance.current` переключается на v0.2 pair;
- README governance requirement в `integration.docs[*].must_reference_files` монотонно дополняется v0.2 paths, сохраняя v0.1 references;
- control/co-change rules не ослабляются.

Accepted v0.1 files не редактируются.

## Failure и rollback semantics

До merge каждая транзакция остаётся изолированной веткой/PR. Если test preparation, docs preparation или governance promotion RED, main не меняется.

Особенно для транзакции C запрещено частичное продвижение: current policy не должен указывать на pair, у которой отсутствует второй artifact, нарушена cross-reference или не пройдены exact-head gates.

Если repo-guard или product CI обнаруживает необходимость semantic/product изменения, promotion останавливается; scope не расширяется молча.

## Verification и merge discipline

Для каждой транзакции перед merge обязательны:

- fresh `main`;
- exact PR head;
- `behind_by=0`;
- `repo-guard` GREEN;
- stable `ci-required` GREEN;
- отсутствие unresolved review threads/blockers;
- merge с fixed expected head SHA;
- post-merge reread свежего `main`.

Поскольку repository settings пока не дают branch protection как окончательный trust boundary, fixed-head discipline остаётся обязательной.

## Последовательность после v0.2

```text
-> B. README preparation
-> C. accepted v0.2 governance promotion
-> #98 executable requirement -> vector -> evidence graph

```
