# GitLab CI: платформенные сборки и публикация версии

Документ описывает переносимый контракт продукта. Имена инфраструктуры, адреса и значения CI/CD-переменных задаются во внешнем GitLab после копирования каталога `webassist/`.

## Стадии

Конвейер разделён на три ответственности:

1. `utility-tasks` — ручная первичная настройка хранилища и переменной конфигурационного репозитория.
2. `build` — независимые платформенные сборки и публикация их проверенных неизменяемых байтов во внешнее хранилище.
3. `publish` — публикация общего номера продукта только после успешного завершения **всех** задач стадии `build`.

Текущая платформенная задача — `build-altlinux-release`. Дополнительные платформы, включая Windows, добавляются отдельными задачами стадии `build`; `publish-release-version` при этом не меняется.

## Подготовка

На GitLab Runner доступен образ `${CI_DOCKER_HUB}/webassistant-builder:${WEBASSISTANT_BUILDER_TAG}` (по умолчанию `dotnet-10.0.403-v1`).

Групповые переменные `CI_BUILD_PROJECT_PATH`, `CI_SSH_HOST`, `CI_SSH_USER`, `CI_SSH_ID_RSA` и необязательная `CI_SSH_ID_RSA_SECRET` задают внешнее хранилище неизменяемых релизов. `CI_BUILD_PROJECT_PATH` указывает непосредственно на существующий общий каталог `products`.

Ручная задача `prepare-release-storage` создаёт только `${CI_BUILD_PROJECT_PATH}/${CI_PROJECT_NAME}` с правами `0750`. Корневой каталог уже существует.

Ручная задача `create-release-config-variable` использует внешний `CI_GITLAB_API_ACCESS_TOKEN` для GitLab API и создаёт защищённую переменную проекта `CI_RELEASE_CONFIG_REPO=null`, если её ещё нет. Администратор устанавливает имя конфигурационного репозитория и предоставляет `CI_GITLAB_CICD_AGENT_USER` вместе с `CI_GITLAB_CICD_AGENT_SECRET`.

SSH-ключ загружается через `ssh-agent` и `SSH_ASKPASS` без вывода секрета в журнал. Проверка ключа хоста использует `known_hosts` и `StrictHostKeyChecking=accept-new`: неизвестный ключ принимается при первом контакте, а изменившийся относительно сохранённой записи отклоняется. Для строгого доверия к серверу инфраструктура Runner должна предварительно предоставить доверенные ключи хоста.

## Платформенная сборка

`build-altlinux-release` на основной ветке:

1. проверяет `CI_PROJECT_NAME`, ревизию исходников и контракт SSH/хранилища;
2. читает общий `VERSION`;
3. вызывает канонический `build/linux/package.sh`;
4. проверяет ZIP, контрольную сумму и данные происхождения;
5. формирует `manifest.json`;
6. передаёт те же байты через SSH;
7. на хосте хранилища выполняет последовательность «копирование → проверка → удаление временного каталога».

Текущий относительный путь:

```
<CI_PROJECT_NAME>/releases/<VERSION>/
  manifest.json
  altlinux-x64/
    <installerBaseName>-linux-x64-<VERSION>.zip
    <installerBaseName>-linux-x64-<VERSION>.zip.sha256
    <installerBaseName>-linux-x64-<VERSION>.zip.provenance.json
```

Повторная публикация версии допустима только при полном совпадении байтов. Отличающийся или неполный релиз отклоняется. Наличие каталога `releases/<VERSION>/` само по себе не является сигналом готовности: готовность определяется успешным завершением платформенной задачи и проверкой байтов.

При прерывании транзакции может остаться `.publish-lock`. Перед его ручным удалением необходимо проверить временный и конечный каталоги релиза и убедиться, что публикация действительно завершилась или остановилась.

## Публикация общего VERSION

`publish-release-version` находится в отдельной стадии `publish`. GitLab запускает её после успешного завершения всех платформенных задач стадии `build`.

Задача проверяет `CI_RELEASE_CONFIG_REPO`, `CI_GITLAB_CICD_AGENT_USER`, `CI_GITLAB_CICD_AGENT_SECRET`, `CI_PROJECT_NAMESPACE` и `CI_SERVER_URL`, затем коммитит одну строку:

```
<CI_PROJECT_NAME>/release-version.txt
```

Каталог продукта в конфигурационном репозитории должен существовать. Равная версия не создаёт изменений; понижение версии и принудительная отправка запрещены; конфликт параллельной отправки обрабатывается ограниченным повтором.

Имя пользователя и секрет передаются Git через `GIT_ASKPASS`; оба значения задаются внешними CI-переменными. HTTPS используется по умолчанию; HTTP допускается только явной приватной настройкой `CI_RELEASE_CONFIG_ALLOW_HTTP=1`.

CI конфигурационного репозитория самостоятельно копирует выбранные байты релиза между хранилищами, проверяет манифест и SHA-256 и последним переключает указатель канала. Продуктовый конвейер не содержит идентичностей целевых кластеров и не пересобирает артефакты при продвижении.

## Восстановление после ошибки публикации VERSION

Если все обязательные задачи стадии `build` успешно опубликовали байты, а `publish-release-version` завершилась ошибкой при записи в конфигурационный Git-репозиторий, после устранения причины повторно запускается **только эта упавшая задача в том же конвейере**. Полная пересборка той же `VERSION` не требуется и нежелательна: новый запуск упаковщика может дать другие байты, которые неизменяемое хранилище обязано отклонить как конфликт.

## Добавление платформ

Новая платформа считается частью общего релиза только если её задача сборки обязательна для соответствующего конвейера релиза: она запускается вместе с остальными платформами, не является ручной или необязательной, не допускает игнорирования ошибки и при сбое блокирует переход к стадии `publish`.

Этот срез обобщает только оркестрацию и публикацию общего `VERSION`. Текущий манифест и раскладка неизменяемого релиза остаются специфичными для ALT Linux; многоплатформенная транзакция хранения и общий манифест проектируются отдельно в #315.
