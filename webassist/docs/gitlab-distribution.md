# GitLab CI: ALT Linux immutable release

Этот документ описывает только переносимый контракт продукта. Все имена
инфраструктуры, адреса и значения CI/CD-переменных задаются **во внешнем
GitLab-проекте** после копирования корня продукта.

## Подготовка

1. На GitLab Runner доступен образ `${CI_DOCKER_HUB}/webassistant-builder:${WEBASSISTANT_BUILDER_TAG}` со средствами сборки, проверки и публикации. Тег по умолчанию — `dotnet-10.0.403-v1`.
2. В **групповых** CI/CD-переменных настроены `CI_BUILD_PROJECT_PATH`, `CI_SSH_HOST`, `CI_SSH_USER`, `CI_SSH_ID_RSA`, а при необходимости парольная фраза `CI_SSH_ID_RSA_SECRET`. `CI_BUILD_PROJECT_PATH` — абсолютный путь к **уже существующему общему каталогу `products` всех проектов GitLab-группы на `CI_SSH_HOST`**. Ручная подготовка и автоматическая сборка используют одно значение.
3. При настройке проекта выполняется manual job `prepare-release-storage`. Она использует тот же SSH-доступ и создаёт **`${CI_BUILD_PROJECT_PATH}/${CI_PROJECT_NAME}`** с правами `750` через `sudo -n install -d`. Общий каталог `products` уже существует и не является символической ссылкой. При отсутствии разрешённого беспарольного `sudo` задача завершается ошибкой.
4. После подготовки на основной ветке выполняется `build-altlinux-release`. Имя продукта определяется встроенной GitLab-переменной `CI_PROJECT_NAME`.

SSH-ключ загружается через `ssh-agent` и `SSH_ASKPASS` без вывода секрета в журнал. Проверка host key использует `known_hosts` и `StrictHostKeyChecking=accept-new`: неизвестный ключ принимается при первом контакте, изменившийся относительно сохранённой записи отклоняется. Для строгого доверия к серверу в инфраструктуре Runner предварительно задаются доверенные host keys.

## Сборка и публикация

Job `build-altlinux-release` запускается на основной ветке:

1. Проверяет встроенное имя проекта `CI_PROJECT_NAME` и `CI_COMMIT_SHA`, затем выполняет локальную предварительную проверку группового `CI_BUILD_PROJECT_PATH`, `CI_SSH_HOST`, `CI_SSH_USER`, `CI_SSH_ID_RSA` и идентификаторов GitLab pipeline/job. Пустые значения, заглушки `null`/`masked_null` и некорректный путь или SSH target завершают job с ошибкой до тестов и упаковки. Парольная фраза `CI_SSH_ID_RSA_SECRET` необязательна; доступность сервера и корректность ключа проверяются при фактической публикации. Затем проверяются `VERSION`, инструменты и SDK 10.
2. Запускает тесты immutable release.
3. Вызывает только canonical `build/linux/package.sh`,
   передавая `WEBASSISTANT_SOURCE_SHA=$CI_COMMIT_SHA`;
   SDK берётся из заранее подготовленного builder image.
4. Находит ровно один ZIP с учётом допустимого custom installer basename.
5. Проверяет ZIP, `.sha256`, `.provenance.json` и формирует
   `<CI_PROJECT_NAME>/releases/<VERSION>/manifest.json`.
6. Проверяет SHA-256, размер, source revision и относительные пути.
7. Передаёт ровно те же bytes через SSH tar stream; на принимающей стороне
   повторно проверяет SHA каждого из четырёх файлов.
8. На storage-host копирует точные файлы из временного каталога
   в новый каталог `releases/<VERSION>/`, повторно проверяет структуру,
   все SHA-256 и полное совпадение с staging, затем удаляет staging
   (`copy → verify → delete`). Готовность релиза определяется успешной
   проверкой артефактов и завершением job. При уже опубликованной
   идентичной версии выполняется no-op; при любых отличиях — FAIL CLOSED.

В manifest `altlinux-x64` является ключом совместимости продукта,
`linux-x64` — техническим .NET RID. Все пути внутри manifest
относительные; инфраструктурные значения в нём отсутствуют.

Во внешнем storage относительный каталог релиза:
`<CI_PROJECT_NAME>/releases/<VERSION>/` (внутри общего каталога `products`, указанного в `CI_BUILD_PROJECT_PATH` на `CI_SSH_HOST`).
Артефакты установщика сохраняются непосредственно во внешнем storage. Автоматическая публикация требует подготовленного каталога проекта; его создание выполняет ручная задача `prepare-release-storage`.

Внешние контуры доставки получают уже опубликованные и проверенные файлы из `CI_BUILD_PROJECT_PATH` и копируют их на собственные диски под управлением отдельных инфраструктурных конвейеров. Путь целевого диска, HTTP-домен и политика автоматического либо ручного продвижения не входят в конфигурацию сборки WebAssistant.

**Важная семантика публикации:** наличие каталога
`releases/<VERSION>/` может существовать до завершения копирования. При
`copy → delete` конечный каталог может временно содержать лишь
часть файлов; если копирование оборвалось, частичный каталог остаётся.
Потребитель (будущий promotion pipeline) должен ждать успешного
завершения `build-altlinux-release` и **самостоятельно проверять
manifest и SHA-256 каждого артефакта**; существование каталога само по себе
не является признаком готовности. Повторная публикация с отличающимися
или неполными байтами отклоняется; удаление частичного каталога требует
ручного анализа.

При прерывании транзакции может остаться `.publish-lock` — прежде
чем удалять его, нужно проверить staging и конечный каталог.
Обновление promotion descriptor, release index и channel pointers
остаётся отдельным этапом, и channel pointer публикуется последним.

## Локальная проверка

На Linux с bash, jq и coreutils:

    bash tests/distribution-release.test.sh

Тестируются сборка, верификация, custom installer basename,
повреждённые байты, лишние файлы, повторная идентичная публикация
и запрет перезаписи. Это не заменяет проверку реального GitLab
builder, сетевой ФС и целевой ALT Linux системы.


## Передача номера релиза в конфигурационный репозиторий

В настройках GitLab-проекта ручная задача `create-release-config-variable` создаёт
защищённую project-scoped переменную `CI_RELEASE_CONFIG_REPO=null`, не изменяя существующее
значение при повторном запуске. Администратор указывает имя конфигурационного репозитория,
расположенного в `CI_PROJECT_NAMESPACE`. Для создания переменной требуется
`CI_PROJECT_ACCESS_TOKEN` с правами управления CI/CD-переменными.

`build-altlinux-release` перед сборкой проверяет `CI_RELEASE_CONFIG_REPO`,
`CI_GITLAB_CICD_AGENT_USER`, `CI_GITLAB_CICD_AGENT_SECRET`, `CI_PROJECT_NAMESPACE` и `CI_SERVER_URL`.
После успешной верификации и SSH-публикации **тех же байтов** в хранилище
вызывается `publish-config-version.sh`; он коммитит одну строку
`<CI_PROJECT_NAME>/release-version.txt` в default branch конфигурационного GitLab-репозитория.

Каталог `<CI_PROJECT_NAME>/` должен уже находиться под управлением Git.
Повтор одинаковой версии является no-op, downgrade запрещён, push не использует force;
конфликт параллельных коммитов обрабатывается повторной загрузкой и ограниченными попытками.
Имя пользователя и секрет передаются Git через `GIT_ASKPASS`; оба значения задаются внешними CI-переменными и не помещаются в remote URL или текст коммита.

Предпочтителен HTTPS. Для GitLab с разрешённым только HTTP существует **явное**
частное согласование `CI_RELEASE_CONFIG_ALLOW_HTTP=1`, которое допускает передачу
credential без TLS и должно рассматриваться как риск до включения HTTPS.

Выбор версии downstream-контуром и копирование релиза между хранилищами не выполняются
в продуктовом pipeline. Подтверждение успешной записи версии не заменяет
самостоятельной проверки manifest и SHA-256 принимающей стороной.

Локальная проверка:
`bash tests/promotion-version.test.sh` (только временный Git-репозиторий, без сетевого GitLab).
